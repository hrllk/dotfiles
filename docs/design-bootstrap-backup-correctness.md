> **Scope carve-out.** 이 문서는 [design-bootstrap-units.md](design-bootstrap-units.md)
> 백로그 24건 중 4건만 떼어낸 것입니다. 단위 분리(`scripts/bootstrap.d/`)는 하지
> 않습니다. 번호는 새로 매기지 않고 원 백로그의 **T6 / T5 / T7 / T3**를 그대로
> 씁니다. 같은 작업에 번호 체계가 하나 더 생기면 방금 정리한 문제가 재발합니다.

## Problem Statement

`scripts/bootstrap.sh`의 백업과 clone 경로에 세 개의 회귀가 있고, 그것을 검증할
테스트 하나가 실제 저장소를 대상으로 실행됩니다. 넷 다 단위 분리와 무관하게 지금
고칠 수 있으며, 단위 분리를 기다리면 그 리팩터가 잘못된 동작을 그대로 옮겨 담습니다.

### T6 — 백업이 `$HOME`에 떨어지는데 `$BACKUP_ROOT`라고 보고한다

`scripts/bootstrap.sh:109`가 첫 후보 경로를 `$HOME/${base}.bak.${TIMESTAMP}`로
만듭니다. `$BACKUP_ROOT`는 충돌이 났을 때 도는 루프(`:114`)에서만 쓰입니다. 충돌이
없는 일반 경로에서 백업은 홈 디렉터리에 떨어집니다.

격리된 HOME에서 `--dry-run`으로 실측한 출력입니다.

```
dry-run: mv .../home/.zshrc .../home/.zshrc.bak.20260901-120000
backup: .zshrc -> .zshrc.bak.20260901-120000
bootstrap completed. backups: .../home/.dotfiles-backup timestamp: 20260901-120000
```

세 줄이 서로 어긋납니다. `mv` 목적지는 `$HOME`이고, `:125`의 `backup:` 줄은
`safe_label`로 basename만 찍어서 디렉터리를 숨기고, `:228`의 완료 줄은 정작 비어
있는 `$BACKUP_ROOT`를 가리킵니다. 사용자는 백업을 찾으라고 안내받은 곳에서 아무것도
찾지 못합니다.

같은 함수 안에서도 일관되지 않습니다. 1초 안에 두 번 실행하면 첫 백업은 `$HOME`,
두 번째는 `$BACKUP_ROOT`에 놓입니다.

올바른 구현은 이미 저장소에 있습니다. `ai/.claude/scripts/link-claude-home:68`은
첫 후보부터 `$BACKUP_ROOT`를 씁니다.

### T5 — 실패한 백업이 성공 메시지를 찍는다

`scripts/bootstrap.sh:119-126`의 `backup_with_timestamp`는 마지막 문장이 `printf`
입니다. `:124`의 `mv`가 실패해도 함수의 반환값은 `printf`의 것, 즉 0입니다.

`set -euo pipefail`이 `:2`에 있지만 실제 호출 경로에서는 무력합니다.
`run_shell_stage:190`은 `link_path ... || return 20`, `:186`은
`clone_if_missing ... || { ... }` 형태이고, 함수가 `||` 문맥에서 호출되면 그 서브트리
전체에서 `set -e`가 꺼집니다. 프로덕션과 같은 형태로 실측한 출력입니다.

```
mv: rename .../home/sub/.zshrc to .../home/.zshrc.bak.20260901-120000: Permission denied
backup: .zshrc -> .zshrc.bak.20260901-120000
ln: .../home/sub/.zshrc: File exists
link_path returned 1
```

가운데 줄이 거짓입니다. 백업은 일어나지 않았고 원본은 제자리에 있습니다. 상위
호출자가 `ln` 실패로 20을 반환하므로 조용한 데이터 손실은 아닙니다. 문제는 출력이
기계의 상태를 잘못 알려준다는 것입니다. 사용자는 `.zshrc`가 백업됐다고 읽고 실제로는
아닌 상태에서 다음 판단을 합니다.

`set -e`를 신뢰할 수 없다는 점은 원 백로그가 이미 확정 규약으로 못박았습니다
(`모든 unit_* 함수는 명시적 return 0으로 끝난다`, `set -e를 안전망으로 신뢰하지 않는다`).
이 수정은 그 규약을 현행 코드에 처음 적용하는 지점입니다.

### T7 — 중단된 clone이 영구히 방치된다

`scripts/bootstrap.sh:147`이 `[[ -d "$target/.git" ]] && return 0`로 판정합니다.
`.git` 디렉터리의 존재만 봅니다. 네트워크가 끊겨 중단된 `git clone`은 `.git`을 남기고
작업 트리는 비어 있는 상태로 끝나므로, 이후 bootstrap은 그 디렉터리를 영구히
건너뜁니다. 재실행으로 복구되지 않고 사용자는 플러그인이 없는 이유를 알 수 없습니다.

대상은 `run_shell_stage:186-190`의 5개 clone입니다. powerlevel10k, fzf-tab,
zsh-autosuggestions, zsh-syntax-highlighting, tpm.

### T3 — 백업 계약 테스트가 실제 저장소를 대상으로 실행된다

`scripts/tests/claude-backup-contract-test.sh:13`이 `DOTFILES_DIR="$REPO_ROOT"`를
넘기고 `:15`가 헬퍼를 `--yes`로 실행합니다. HOME과 BACKUP_ROOT는 임시 디렉터리로
격리했지만 `DOTFILES_DIR`만 실제 작업 트리를 가리킵니다.

헬퍼의 `merge_into_source`(`link-claude-home:92`)는
`rsync -a --ignore-existing "$path"/ "$SOURCE_DIR"/`를 실행하고, 여기서
`$SOURCE_DIR`는 `$REPO_ROOT/ai/.claude`입니다. 지금은 픽스처
(`$TEST_ROOT/home/.claude`)가 비어 있어서 rsync가 아무것도 복사하지 않으므로
무해합니다. 코드가 안전한 것이 아니라 입력이 비어 있을 뿐입니다.

이것이 T2와 T4보다 먼저 와야 하는 이유입니다. 두 작업은 마이그레이션 누출을
검증하려고 정확히 그 픽스처를 채웁니다. 순서가 바뀌면 테스트가 public 저장소로
런타임 파일을 실제로 흘리고, 그걸 검증하려던 테스트가 사고의 원인이 됩니다.

## What Makes This Useful

bootstrap은 새 Mac에서 처음 실행하는 명령이고 실패를 되돌릴 수단이 백업뿐입니다.
백업이 안내된 곳에 없거나(T6) 안 됐는데 됐다고 나오면(T5) 그 수단이 없는 것과
같습니다. T7은 재실행이라는 유일한 복구 수단을 무력화합니다. T3은 다음 작업이
저장소를 오염시키는 것을 막습니다.

## Constraints

- bash 3.2.57 대상. `declare -A` 금지, nameref 금지, `mapfile` 금지.
- `set -e`를 안전망으로 신뢰하지 않는다. `||` 문맥에서 서브트리 전체가 무력화된다.
- 종료코드 기존 계약 유지: 2 사용법, 10 preflight, 20 apply, 30 secrets sync.
  drift 11은 `--check`가 없는 현행 코드에는 아직 해당하지 않는다.
- 단위 분리(`scripts/bootstrap.d/`)는 이 문서 범위 밖이다.
- `scripts/tests/post-refactor-smoke-test.sh`가 계속 통과해야 한다.
- `bootstrap-matrix-test.sh:31`이 사용법 오류에 2를 assert한다. 건드리지 않는다.

## Premises

1. 네 항목은 서로 의존하지 않는다. 어떤 순서로도 개별 착수할 수 있다.
2. `link-claude-home:63-74`가 `backup_path_for`의 올바른 동작을 이미 정의한다.
3. 백업 경로 계산과 백업 실행은 분리 가능하다. 전자는 순수 함수다.
4. 중단된 clone은 `git -C "$target" rev-parse --verify HEAD`로 판별할 수 있다.
5. 테스트가 저장소를 건드리지 않는다는 것은 `git status --porcelain`으로 검증 가능하다.

## Approaches Considered

### Approach A: 네 곳을 제자리에서 최소 수정

`bootstrap.sh:109`의 `$HOME`을 `$BACKUP_ROOT`로 바꾸고, `backup_with_timestamp`에
`mv` 성공 확인과 명시적 `return`을 넣고, `clone_if_missing`에 `rev-parse` 검증을
추가하고, 테스트에 임시 `DOTFILES_DIR` 픽스처를 만든다.

Completeness: 7/10. 네 증상은 사라지지만 `backup_path_for`가 두 파일에 두 벌로
남는다.

장점:

- 변경 표면이 가장 작다. 리뷰가 쉽다.
- 단위 분리와 충돌하지 않는다. T8이 나중에 그대로 추출한다.
- 회귀 위험이 낮다.

한계:

- 두 구현이 여전히 손동기화 대상이다. 갈라진 전례가 이미 있다(T6 자체).
- T6의 원 지시("link-claude-home 구현으로 승격")를 절반만 만족한다.

### Approach B: `backup_path_for`를 지금 공용 파일로 추출

`scripts/bootstrap.d/lib.sh`를 이 4건을 위해 미리 만들고 두 스크립트가 source한다.

Completeness: 10/10 for the duplication problem.

장점:

- 중복이 지금 사라진다. T6이 다시 갈라질 수 없다.
- T8의 절반을 미리 처리한다.

한계:

- `scripts/bootstrap.d/`를 단위 없이 먼저 만든다. 디렉터리 이름이 아직 없는 구조를
  약속한다.
- `link-claude-home`은 단독 실행되는 스크립트다. source 경로 해석과 `--dry-run`
  전파 규약(T12)이 아직 확정되지 않았다.
- T8/T12의 결정을 이 문서가 선점한다. 원 백로그의 D5 3단계 순서를 어긴다.

### Approach C: A로 고치고 두 구현이 같음을 테스트로 고정

A를 적용한 뒤, 두 `backup_path_for`가 동일한 입력에 동일한 출력을 내는지 확인하는
assertion을 추가한다. 추출은 T8에 맡긴다.

Completeness: 9/10. 중복은 남지만 갈라짐은 테스트가 막는다.

장점:

- A의 낮은 위험을 유지하면서 B가 풀려는 문제를 다룬다.
- T8이 추출할 때 그 테스트가 회귀 감시로 그대로 쓰인다.
- D5 3단계 순서를 어기지 않는다. 테스트가 먼저다.

한계:

- assertion 하나를 T4의 14개 목록보다 먼저 쓰게 된다. 테스트 파일 소유권이 잠시
  모호하다.
- 두 구현의 계약(전체 경로 인자 대 basename 인자)을 먼저 통일해야 한다.

## Recommended Approach

Approach C를 제안합니다.

A의 변경 표면과 B의 중복 방지를 동시에 얻고, 원 백로그가 확정한 "테스트가 리팩터
안전망"이라는 순서를 지킵니다. 두 `backup_path_for`의 시그니처 차이(bootstrap은 전체
경로를 받아 내부에서 `safe_label`, link-claude-home은 basename을 받음)를 통일하는
것이 이 접근의 실제 작업량입니다.

`link-claude-home:73`의 `printf '%s/%s\n' "$BACKUP_ROOT" "${candidate#"$BACKUP_ROOT/"}"`
는 `$BACKUP_ROOT`를 떼고 다시 붙이는 항등 연산입니다. 승격할 때 `printf '%s\n' "$candidate"`
로 정리합니다.

## Resolved Decisions

CEO review 2026-09-01, HOLD SCOPE mode. 세 결정은 `~/.gstack`의 decision log에도 기록했습니다.

- **D1 — 중복 처리 범위: Approach C.** 다섯 곳을 제자리에서 고치고, 두 `backup_path_for`가 동일 입력에 동일 출력을 낸다는 assertion을 추가합니다. 실제 추출은 T8이 합니다. S-04가 이미 단순 복사 상태에서 갈라진 전력이 있으므로 사람이 아니라 테스트가 동일성을 지킵니다.
- **D2 — 손상된 clone 처리: 기존 백업 경로.** `backup_with_timestamp`를 타서 `$BACKUP_ROOT`로 이사합니다. 이 저장소의 모든 파괴적 동작은 백업을 거치며 clone 잔해만 예외를 두지 않습니다. 부작용으로 `.git`만 있는 디렉터리가 백업 루트에 쌓입니다. 감수합니다.
- **D3 — 과거 `$HOME` 백업 안내: 마이그레이션 노트 유지.** `reference-bootstrap-cli.md`의 버그 설명과 S-04 포인터는 지우고, 그 자리에 "2026-09-01 이전 버전은 첫 backup을 홈에 생성했다"는 세 줄을 남깁니다. 이 기계에 이미 그 백업이 있을 가능성이 높습니다.

### 통일된 `backup_path_for` 계약

인자는 **전체 경로**를 받습니다. bootstrap 쪽 호출자(`link_path`, `clone_if_missing`)가 전체 경로를 갖고 있고, link-claude-home 쪽(`move_to_backup:79`)만 `basename`을 한 번 벗기면 됩니다. 반대 방향은 호출자 두 곳을 바꿉니다.

`link-claude-home:73`의 `printf '%s/%s\n' "$BACKUP_ROOT" "${candidate#"$BACKUP_ROOT/"}"`는 접두사를 떼고 다시 붙이는 항등 연산입니다. `printf '%s\n' "$candidate"`로 정리합니다.

`bootstrap.sh:108`의 `local base="$(safe_label "$target")"`는 이 저장소가 확정한 bash 3.2 규약(`local x="$(cmd)" 금지 — declare 후 assign`)을 위반합니다. 같은 줄을 어차피 건드리므로 함께 고칩니다.

## Success Criteria

CEO review에서 4건 추가(1, 7, 11, 12)하고 1건을 강화했습니다. 원안의 1번은
`--dry-run` 출력으로 검증한다고 썼는데 dry-run은 계산된 경로 문자열만 증명합니다.

1. **격리 HOME에서 실제 실행** 시 백업 파일이 `$BACKUP_ROOT` 아래에 존재하고 `$HOME`에는 `*.bak.*`가 0개다. (강화: dry-run이 아니라 실제 실행)
2. `backup:` 출력이 basename이 아니라 절대경로를 포함한다.
3. 완료 줄이 가리키는 디렉터리에 실제로 백업이 있다.
4. `mv` 또는 `mkdir`이 실패하면 `backup:` 줄이 나오지 않고 `backup_with_timestamp`가 비0을 반환한다. `||` 문맥에서 호출해도 동일하다.
5. `.git`만 있고 HEAD가 없는 디렉터리로 재실행하면 백업 후 재clone이 일어난다.
6. 이미 정상 clone된 디렉터리로 재실행하면 재clone이 일어나지 않는다.
7. **재clone 시 이유가 stdout에 남는다.** `re-cloning <name>: existing checkout has no HEAD` 형태. (신규: Section 8 gap)
8. 두 `backup_path_for`가 동일 입력에 동일 출력을 낸다.
9. `claude-backup-contract-test.sh` 실행 후 `git status --porcelain`이 비어 있다. 픽스처에 `hooks/x.sh`와 `skills/y/SKILL.md`를 넣어도 그렇다.
10. `post-refactor-smoke-test.sh` 전체 통과. 기존 dry-run assertion 2건(`bootstrap-rerun-test.sh:24`, `bootstrap-matrix-test.sh:62`)이 깨지지 않는다.
11. **`$BACKUP_ROOT`가 쓰기 불가일 때 첫 백업에서 비0으로 실패한다.** 조용히 `$HOME`에 쓰지 않는다. 의도된 동작 변경이며 회귀가 아니다. (신규: Section 1)
12. **문서 3곳이 단일 위치를 서술한다.** `reference-bootstrap-cli.md`에서 S-04 포인터가 사라지고 D3 마이그레이션 노트가 있다. (신규: S-25)
13. `bash 3.2`에서 동작한다. `local x="$(cmd)"` 패턴이 남아 있지 않다.

### 알려진 한계 (Success Criteria 아님)

- `.git`이 유효하고 HEAD도 있으나 worktree가 비어 있는 clone은 `rev-parse HEAD`가 성공하므로 T7이 잡지 못한다.
- D2에 따라 `.git`만 있는 잔해가 `$BACKUP_ROOT`에 누적된다.
