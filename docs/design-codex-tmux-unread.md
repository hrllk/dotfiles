## Problem Statement

tmux 안에서 Codex를 실행한 뒤 완료 callback이 오면, 사용자가 다른 window를 보고 있을 때 해당 Codex window를 쉽게 식별할 수 있어야 한다. 완료 window가 현재 focus되어 있으면 표시가 남지 않아야 하며, 다른 window를 보다가 해당 window로 돌아오면 읽음 처리처럼 완료 표시가 제거되어야 한다.

현재 archive에 있는 hook은 완료 시 `window-status-style`을 직접 덮어쓴다. 이 방식은 원래 window 스타일을 보존하지 못하고, window 접근 이후의 읽음 처리를 표현하지 못한다. 활성 `ai/.codex/` 디렉터리에는 현재 hook 설정이 확인되지 않았으므로 실제 연결 경로도 구현 전에 확인해야 한다.

## What Makes This Useful

완료 알림을 별도 메시지나 desktop notification에 의존하지 않고 tmux window 목록에서 지속적으로 확인할 수 있다. 사용자가 다른 작업을 계속하다가 Codex 결과가 준비된 window로 돌아오는 순간 표시가 자동으로 사라져, 알림이 실제 읽음 상태처럼 동작한다.

## Constraints

- tmux 3.7b에서 동작해야 한다.
- 기존 `window-status-style`, `window-status-current-style`, format을 불필요하게 파괴하지 않아야 한다.
- Codex Stop hook은 대상 pane/window를 정확히 식별해야 한다.
- 완료 상태는 window별로 독립적이어야 한다.
- 외부 daemon, polling, 지속 실행 프로세스는 사용하지 않는다.
- 일반적인 단일 tmux client 사용을 우선 지원한다.
- 여러 client가 같은 session을 보는 경우 client별 unread 상태는 별도 확장 범위다.

## Premises

1. 완료 상태는 Codex 프로세스가 실행된 origin window에 귀속된다.
2. 현재 요구사항에서 focus는 tmux의 active window 선택 상태를 의미한다.
3. 완료 표시와 원래 window 스타일은 분리되어야 한다.
4. 읽음 처리는 사용자가 해당 window를 선택하거나 client focus가 들어오는 이벤트에서 수행할 수 있다.
5. tmux user option과 native hook으로 필요한 상태 전이를 외부 상태 파일 없이 표현할 수 있다.

## Approaches Considered

### Approach A: Native event state

Stop hook은 대상 window에 `@codex_unread=1`을 기록한다. `window-status-format`과 `window-status-current-format`은 이 값이 있을 때만 완료 색상 fragment를 추가하고, `after-select-window` 및 `client-focus-in` hook은 현재 window의 플래그를 제거한다.

Completeness: 10/10 for the stated single-client workflow.

장점:

- 기존 스타일을 직접 덮어쓰지 않는다.
- 완료, 표시, 읽음 처리가 분리된다.
- tmux native event와 user option을 활용해 polling이 없다.
- stale 외부 파일을 정리할 필요가 없다.

한계:

- 동일 window를 여러 client가 볼 때 unread 상태가 client별로 분리되지 않는다.
- 실제 active Codex hook 연결 경로를 먼저 확인해야 한다.

### Approach B: Hook 중심의 직접 스타일 변경

Stop hook이 active window인지 판정한 뒤 비활성일 때 `window-status-style`을 변경하고, window 선택 시 원래 스타일을 복구한다.

Completeness: 8/10.

장점:

- 설정 변경량이 적다.
- 현재 archive hook에서 빠르게 출발할 수 있다.

한계:

- 원래 스타일을 안전하게 기억하고 복구해야 한다.
- theme 또는 사용자의 runtime 설정이 바뀌면 복구 값이 stale해질 수 있다.
- 표시와 상태가 결합되어 이후 기능 확장이 어렵다.

### Approach C: External state registry

Stop hook이 window ID와 완료 상태를 외부 파일 또는 작은 registry에 기록하고, tmux status format이 이를 조회한다.

Completeness: 10/10 for multi-client extensibility.

장점:

- client별 상태와 여러 Codex 작업 ID를 확장하기 쉽다.
- tmux user option의 범위를 넘어선 상태 모델을 만들 수 있다.

한계:

- status refresh마다 외부 명령을 실행할 가능성이 있다.
- stale 상태, 동시 쓰기, session/window 삭제 정리가 필요하다.
- 현재 요구사항에 비해 운영 복잡도가 크다.

## Recommended Approach

Approach A를 선택한다.

구체적으로는 다음 상태 전이를 사용한다.

```text
Codex Stop hook
  -> origin window에 @codex_unread=1 기록
  -> origin window가 현재 active이면 즉시 @codex_unread 제거
  -> 비활성 window이면 플래그 유지

tmux after-select-window / client-focus-in
  -> 접근한 window의 @codex_unread 제거

window-status-format
  -> @codex_unread=1일 때만 완료 색상 fragment 표시
```

완료 hook은 상태 기록과 알림만 담당한다. 원래 tmux style을 저장하거나 복구하지 않는다. 상태 표시를 format fragment로 구현해 기존 active/inactive window style과 충돌하는 범위를 최소화한다.

## Open Questions

- 활성 Codex 설정이 `ai/.codex/`인지, 별도의 home symlink 경로인지 확인해야 한다.
- 활성 Codex 설정은 `~/.codex -> ai/.codex` symlink를 통해 저장소의 `ai/.codex/`를 사용한다. hook과 `hooks.json`은 이 경로에 복원한다.
- “focus”를 tmux active window로 한정할지, terminal client focus-in/out까지 포함할지 결정해야 한다.
- 여러 tmux client가 동일 session을 보는 환경에서 첫 번째 client가 읽음 처리하는 동작을 허용할지 확인해야 한다.
- 완료 색상은 현재 foreground 색상 체계와 충돌하지 않는 단일 foreground color로 할지, bold/배경색을 함께 사용할지 정해야 한다.
- 동시에 여러 Codex 작업이 같은 window에서 끝나는 경우 하나의 unread bit로 합쳐도 충분한지 확인해야 한다.

## Success Criteria

1. Codex가 비활성 window에서 완료되면 해당 window가 지정된 foreground color로 표시된다.
2. Codex가 현재 active window에서 완료되면 표시가 남지 않는다.
3. 다른 window에서 해당 window로 이동하면 완료 표시가 제거된다.
4. 기존 current/inactive window 스타일이 완료 표시 처리 후에도 유지된다.
5. 서로 다른 window에서 완료된 Codex 작업이 독립적으로 표시된다.
6. tmux server를 재시작하거나 설정을 reload해도 hook이 중복 등록되지 않는다.
7. tmux 밖에서 실행된 Codex에는 오류나 불필요한 출력이 발생하지 않는다.
8. 동일 window에서 완료 hook이 반복 실행되어도 상태가 깨지지 않는다.

## Amendment (2026-08-27): Claude Code 확장과 공용화

원래 설계는 Codex 전용이었습니다. 동일한 완료 표시를 Claude Code에도 적용하면서 아래를 변경했습니다.

### 변경 내용

- 상태 변수를 `@codex_unread`에서 `@ai_unread`로 이름 변경했습니다. 필요한 정보는 "이 window에 확인하지 않은 완료가 있다"이지 어느 agent가 끝냈는지가 아니며, 후자는 window 이름과 내용이 이미 알려줍니다. 변수를 agent별로 나누면 `window-status-format`이 중첩 조건으로 복잡해지고 고정 hook slot도 하나 더 필요합니다.
- hook script를 `ai/.codex/tmux-notify-hook.sh`에서 `util/tmux/.tmux/scripts/ai-notify-hook.sh`로 옮기고 agent label을 첫 번째 인자로 받게 했습니다. `~/.tmux`는 이미 저장소로 심링크되어 있어 두 agent 모두 추가 배포 경로 없이 참조합니다. 거의 동일한 script를 두 벌 유지하면 한쪽만 고쳐지는 문제가 생깁니다.
- Codex는 `ai/.codex/hooks.json`, Claude Code는 `ai/.claude/settings.json`의 `hooks.Stop` 배열로 등록합니다. Claude Code는 별도 hook 파일 없이 기존 settings에 항목을 추가하는 방식입니다.

### Claude Code 고유 제약

- **`Stop` 발화 빈도.** `codex exec`는 배치성이라 `Stop`이 드물지만 Claude Code는 assistant turn마다 발화합니다. 그래서 `display-message`와 `kitten notify`를 `window_active != 1`인 경우로 제한했습니다. unread flag 자체는 활성 window에서 0으로 쓰는 기존 분기가 그대로 처리합니다.
- **`SubagentStop`은 등록하지 않습니다.** Task subagent마다 발화하므로 한 turn에 수십 번 실행됩니다.
- **exit code 2 금지.** Claude Code는 `Stop` hook의 exit 2를 "멈추지 말고 계속하라"로 해석하고 stderr를 모델에 되먹입니다. script는 모든 경로에서 명시적으로 0을 반환하며, smoke test가 tmux 밖 실행과 label 누락 경로의 exit status를 검증합니다.
- **환경변수 상속.** Claude Code hook은 Claude 프로세스의 자식이므로 tmux pane에서 실행된 세션의 `TMUX`/`TMUX_PANE`를 그대로 받습니다. Codex와 동일하게 동작합니다.

### 알려진 한계

- "focus"는 여전히 tmux active window를 의미합니다. tmux window는 활성인데 터미널 앱 자체가 백그라운드인 경우, 완료가 읽음으로 처리되어 알림이 오지 않습니다. 원래 설계의 focus 정의를 유지한 결과입니다.

### 테스트 위치 이동

smoke test는 공용 컴포넌트를 검증하므로 `ai/.codex/scripts/test-tmux-unread`에서 `scripts/tests/tmux-unread-test.sh`로 옮겼습니다. `scripts/tests/post-refactor-smoke-test.sh`에 연결했고, `ai/.codex/scripts/test`는 존재할 때만 호출하도록 guard를 두어 harness가 저장소 밖에서 실행될 때 조용히 건너뜁니다.
